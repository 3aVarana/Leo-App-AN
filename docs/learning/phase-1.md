# Phase 1: Domain, iOS → Android

**`enum: String, Codable` → `enum class` + `@SerialName`.** Kotlin enums have no raw value built in, so [AgeGroup.kt](../../domain/src/main/kotlin/com/victorarana/leo/domain/AgeGroup.kt) carries one as a constructor property (`rawValue`), and `@SerialName("6-8")` tells kotlinx.serialization what to write. The two are separate: renaming the Kotlin constant (`SIX`) never changes the saved JSON, but editing `@SerialName` does.

**`Codable` → `@Serializable`, generated at compile time.** Swift synthesizes `Codable` in the compiler. Kotlin does the same through the `kotlin-serialization` compiler plugin applied in [domain/build.gradle.kts](../../domain/build.gradle.kts). Unlike Gson or Moshi, it doesn't use reflection, so it works in a pure JVM module and survives R8. Where iOS writes a custom `init(from:)`, [ReaderPreferencesSerializer.kt](../../domain/src/main/kotlin/com/victorarana/leo/domain/ReaderPreferencesSerializer.kt) uses the surrogate pattern: a private `@Serializable` class with defaults decodes the raw JSON, then the real type is built from it, which is where the clamping happens.

**`JSONDecoder` defaults → `Json { … }` flags.** `JSONDecoder` ignores unknown keys, and `decodeIfPresent` treats both "missing" and `null` as absent. kotlinx.serialization is strict by default, so `LeoJson` opts in to each behavior: `ignoreUnknownKeys`, `coerceInputValues` (null → default), and `encodeDefaults`, so all five keys are always written.

**`mutating func` → immutable `data class` + `copy`.** Kotlin has no value-type structs. A `data class` with `val`s and read-only `Map`/`Set` gives the same "no shared mutation" guarantee. Functions return a new instance via `copy(...)`, and maps are updated with `+` (`map + (key to value)`). See `setEnabled` in [ReaderPreferencesTopicEditing.kt](../../domain/src/main/kotlin/com/victorarana/leo/domain/ReaderPreferencesTopicEditing.kt). Swift's `extension ReaderPreferences { … }` becomes top-level extension functions in that file.

**`String(localized:)` in Domain → pass the dependency in.** iOS can look up strings anywhere because `Bundle.main` is global. Android resources need a `Context`, and `:domain` has no Android at all. So domain logic takes a `fun interface TopicNames` (`Topic.kt`), a single-method interface you can pass as a lambda, like a Swift closure type. Tests use `TopicNames.English`, and the app passes [ResourceTopicNames.kt](../../app/src/main/java/com/victorarana/leo/features/components/ResourceTopicNames.kt). That class keeps `applicationContext`, never an Activity: holding an Activity past its lifetime is the classic Android leak, because Activities are destroyed and recreated on rotation.

**`Localizable.xcstrings` → resource folders.** One catalog becomes `values/`, `values-es/` and `values-pt-rBR/strings.xml`. The `-r` prefix marks a region, and the folder qualifier picks the language the way `.lproj` folders did. [DomainLabels.kt](../../app/src/main/java/com/victorarana/leo/features/components/DomainLabels.kt) maps each enum to an `@StringRes Int`, which is the compile-time-checked key that `R.string.x` generates. [DomainLabelsTests.kt](../../app/src/test/java/com/victorarana/leo/features/components/DomainLabelsTests.kt) switches language with Robolectric's `setQualifiers("es")` on the JVM, with no emulator.

**Foundation text APIs → `java.text`.** `enumerateSubstrings(.byWords)` → `BreakIterator.getWordInstance` ([WordCount.kt](../../domain/src/main/kotlin/com/victorarana/leo/domain/WordCount.kt)). Swift's `String.count` counts grapheme clusters, but Kotlin's `String.length` counts UTF-16 units, so an emoji family is 11 not 1; [TextMatching.kt](../../domain/src/main/kotlin/com/victorarana/leo/domain/TextMatching.kt) counts with `getCharacterInstance`. `.diacriticInsensitive` → `Normalizer` NFD then strip combining marks. On a phone these classes are backed by ICU, but in JVM tests they are the JDK's own, so results can differ. Phase 3 adds an on-device check.

**Shared test helpers → the `testFixtures` source set.** iOS's `LeoTests/Support/Fixtures.swift` is visible to every test file in one target. Gradle source sets are per module, so [Fixtures.kt](../../domain/src/testFixtures/kotlin/com/victorarana/leo/domain/Fixtures.kt) lives in `src/testFixtures/` (the built-in `java-test-fixtures` plugin), and `:app` tests can depend on it in later phases with `testImplementation(testFixtures(project(":domain")))`.

**Library versions follow the Kotlin compiler.** SwiftPM packages rarely care which Swift minor version you use. Kotlin libraries are compiled against a specific stdlib, and the compiler reads at most one minor version ahead. kotlinx-serialization 1.12.0 needs Kotlin 2.4, and this project compiles with 2.2, so it is pinned to 1.11.0 (comment in [libs.versions.toml](../../gradle/libs.versions.toml)).
