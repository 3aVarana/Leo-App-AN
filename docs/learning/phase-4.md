# Phase 4: the app shell

**`Application` + `AppContainer` (iOS: `@main struct MyApp: App`).** Android has no `@main` value that owns the app. The OS creates one `Application` per process (named in the manifest's `android:name`) and then starts an `Activity`, which it may destroy and recreate on rotation, dark-mode or language changes. So the long-lived objects go in `LeoApplication.container`, and the Activity only reads from it (`LeoApplication.kt`, `AppContainer.kt`). Every field is `by lazy` because Robolectric creates the `Application` for each test: a cheap one keeps ML Kit, Room and DataStore out of the tests.

**`ViewModel` + factory (iOS: `@State var model = RootViewModel(...)`).** A `ViewModel` outlives Activity recreation; SwiftUI's `@State` outlives view re-evaluation. The system builds the ViewModel, so constructor arguments reach it through a `viewModelFactory { initializer { } }` closure (`MainActivity.kt`). `RootViewModel` exposes one `StateFlow<RootUiState>`, which the screen reads with `collectAsStateWithLifecycle()`. Preferences load asynchronously from DataStore, so the state has a `Loading` step that iOS doesn't need (`RootViewModel.kt`).

**Lifecycle events (iOS: `scenePhase`).** `LifecycleEventEffect(ON_RESUME)` in `RootScreen.kt` re-checks the model each time the app comes back to the foreground. It plays the role of `.onChange(of: scenePhase)`, and it is tied to the composable, so it stops when the screen leaves.

**Gates, then `NavHost` (iOS: `if/else` + `NavigationStack`).** Availability and onboarding are plain state switches in `RootScreen`, exactly as on iOS. Only the onboarded app is inside `NavHost`, whose routes are `@Serializable` objects (`LeoRoute.kt`, `LeoNavHost.kt`). Unlike `NavigationStack(path:)`, the back stack belongs to the `NavController`, and the system Back button pops it with no extra code.

**`CompositionLocal` (iOS: `@Environment` and `PreferenceKey`).** A `CompositionLocal` passes values down the tree like `@Environment` (`LocalReduceMotion` in `features/theme/Accessibility.kt`). Compose has no `PreferenceKey` for sending values up, so the launch intro shares a mutable holder (`LocalLaunchWordmarkTarget`). The header writes its window position into it from `onGloballyPositioned`, and the overlay reads it (`LaunchIntroOverlay.kt`).

**Custom layout (iOS: `Layout` protocol, `ViewThatFits`).** Compose's `Layout { measurables, constraints -> }` is SwiftUI's `sizeThatFits` + `placeSubviews` in one block. A child can be measured only once per pass, and constraints are min/max ranges instead of proposals. `ScrollingScreen.kt` uses it to make spacers split free height the way SwiftUI's do, which a plain `Column` can't. `SubcomposeLayout` measures one candidate before composing another, which is how `AgeSegmentedControl.kt` replaces `ViewThatFits`.

**Font scale and Reduce Motion (iOS: Dynamic Type, `@ScaledMetric`).** Android scales text with a single `fontScale` number, and from Android 14 that scaling is nonlinear: large text grows less. `Dp.scaled(relativeTo)` follows the iOS text style each size belongs to, and `CappedFontScale` stands in for `.dynamicTypeSize(...xxxLarge)` (`Accessibility.kt`). Reduce Motion has no direct API: the closest signal is the system "Remove animations" setting, which sets the animator duration scale to 0.

**Splash screen (iOS: launch screen storyboard).** On Android 12+ the system always draws a splash: a background plus a centered icon. The `core-splashscreen` library makes older versions do the same. The icon is the "Leo" wordmark as a vector traced from the bundled font, placed where the intro's first frame draws it, so the handoff doesn't jump (`MainActivity.kt`, `res/drawable/splash_icon.xml`, `Theme.Leo.Starting` in `themes.xml`).
