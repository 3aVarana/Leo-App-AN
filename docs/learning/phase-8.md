# Phase 8: polish

**`<plurals>` instead of xcstrings plural variations.** Android picks the form from CLDR's categories for the locale. Spanish and Portuguese have `one`, `many` and `other`, and Lint fails the build if one is missing, even though `many` only applies to numbers like a million. You pass the count twice: `pluralStringResource(id, quantity, args…)` picks the form with the first and formats with the rest. That is how `review_count` keys on the total while it shows "1 de 3": `pluralStringResource(R.plurals.review_count, misses.size, selection + 1, misses.size)` (`ReviewScreen.kt`, `values-es/strings.xml`).

**The formatting locale is assembled by hand (iOS: `Locale.current` is already the app's localization plus the device region).** On Android, `Configuration.locales[0]` is the locale the user asked for, not the one the resources resolved to. A French phone gets English strings, because there is no `values-fr`, but a French `ListFormatter` and French month names. Android has no API that says "which `values-xx` won", so each locale's `strings.xml` names its own language in `resource_locale`. `resolvedLocale` then pairs that language with the device's region and its Android 14 regional preferences (`ResolvedLocale.kt`).

**Per-app language is build config, not code (iOS: Settings › Leo › Language comes free with the localizations).** `generateLocaleConfig` writes `locale_config.xml` from your `values-*` folders and puts it in the manifest. `localeFilters` drops the libraries' other languages. `resources.properties` says what the unqualified `values/` is (`en-US`). The catch: once an app language is set, the process configuration, and `Resources.getSystem()` with it, starts with that language. The device's own region is then only available from `LocaleManager.systemLocales` (API 33+). That was review S1 (`deviceLocale`, `app/build.gradle.kts`).

**Source sets instead of `#if DEBUG`.** The stub model is not compiled out by a flag. It is in `app/src/debug/`, and `app/src/release/` has a no-op `StubModelHook` with the same name, so `main` compiles against either. Release has no stub classes at all; the dex check in `changes.md` proves it. A debug-only test goes in `src/testDebug/` (`StubModelHook.kt`, `AppContainer.kt`).

**A lambda that reads a property captures `this`.** Inside `initializer { }` in `MainActivity`, `application` is `this@MainActivity.getApplication()`. A lambda that calls it keeps the Activity alive, and the ViewModel holding that lambda outlives the Activity at every rotation. Swift would have made you write `self.` and think about `[weak self]`; Kotlin hides the capture. The fix is `val app = application` first, which `javap` confirms: the lambda takes an `Application` now. That was review B1 (`MainActivity.kt`).

**The semantics tree is testable data (iOS: Accessibility Inspector, by hand).** `AccessibilityRulesTests` walks every screen's nodes. It checks that clickable nodes have a label, that touch targets are at least 48dp in the *unmerged* tree (the merged tree reports the parent's size), that titles are headings, and that roles have actions. A `SubcomposeLayout` that measures content it never places (our `ViewThatFits`) still adds that content to the semantics tree. `clearAndSetSemantics {}` on the measuring slot removes it (`AgeSegmentedControl.kt`).

**Device shapes are Robolectric qualifiers (iOS: a different simulator per run).** `@Config(qualifiers = "w1280dp-h800dp-land-xhdpi")`, `"+es"` or `"+pt-rBR"` gives the same tests a tablet, a landscape phone or a language, on the JVM. The helper used to append `+h844dp` every time, which silently made every tablet a phone (`SnapshotHelpers.kt`, `snapshots/TabletSnapshotTests.kt`).

**Adaptive icon instead of `AppIcon.icon`.** The launcher masks a 108dp foreground over a background, in whatever shape it likes. A third `monochrome` layer is what Android 13's themed icons tint. Night backgrounds come from `drawable-night/`. There is nothing like Liquid Glass's lighting (`mipmap-anydpi/ic_launcher.xml`).

**Contrast.** iOS's Increase Contrast maps to `UiModeManager.contrast` (API 34+), read since phase 0. This phase adds screen snapshots for it (`HighContrastSnapshotTests`).
